## 포매팅 규칙

- **들여쓰기**: 스페이스 4칸 (탭 사용 금지)
- **줄 길이**: 150자 이하. 150자 미만이면 줄바꿈하지 않는다
- **줄바꿈 기준**: 메서드 체이닝, 파라미터 목록, 조건식이 150자를 넘을 때만 줄바꿈
- **빈 줄**: 관련 없는 블록 사이에만 삽입, 과도한 공백 금지
- `.editorconfig` 설정을 항상 따른다 (프로젝트 루트 참고)

## 설계·유지보수 원칙

- **수정량이 아니라 옳음을 기준으로 한다.** diff를 작게 만들려고 정석적인 설계를 포기하지 않는다. 코드를 더 많이 고쳐야 하더라도 유지보수하기 좋은 우아한 방향을 택한다. "지금 동작하는 가장 쉬운 코드"가 아니라 "다른 개발자가 6개월 뒤 읽고 안전하게 고칠 수 있는 코드"를 작성한다.
- **하드코딩 금지.** 경로·매직 넘버·분기 조건을 코드나 설정에 직접 박지 않는다. 의미 있는 상수, 설정값, 어노테이션/정책 기반의 선언적 방식으로 표현해 변경에 강하게 만든다.
  - 나쁜 예: 게이트웨이 `application.yml`에 차단할 경로 문자열(`Path=/api/auth/balance/deduct`)을 직접 박아 특정 엔드포인트를 막는다.
  - 좋은 예: `@InternalApi` 같은 어노테이션으로 코드 레벨에서 선언적으로 접근을 제어한다.

## 보안 기본 원칙 (요청 여부와 무관하게 항상 적용)

아래 항목은 사용자가 명시적으로 요구하지 않았더라도 **구현의 일부로 반드시 충족한다.** 보안·인가·정합성은 "요구사항 범위 초과"가 아니라 기능을 올바르게 완성하는 일이다. 요청받은 사항만 처리하고 부가적 보안 고려를 빠뜨리지 않는다.

- **인증(Authentication)과 인가(Authorization)를 구분한다.** "로그인했는가"만 확인하고 끝내지 않는다. 리소스를 다루는 모든 엔드포인트에서 "요청자가 이 리소스에 접근/수정할 권한이 있는가"를 검증한다.
- **객체 수준 권한 검증 (IDOR/BOLA 방지).** `{id}`로 단건 리소스를 조회·수정·삭제할 때 그 리소스가 요청자 소유인지 반드시 확인한다. 가능하면 조회 쿼리 자체에 소유자 조건을 건다(예: `findByIdAndUserId`). 타인 리소스 접근은 존재 여부를 노출하지 않도록 404로 응답한다.
- **신뢰 경계를 지킨다.** 클라이언트가 보낸 값(요청 본문의 userId 등)으로 권한을 판단하지 않는다. 인증 컨텍스트(게이트웨이가 검증해 주입한 `X-User-Id` 등)를 기준으로 한다.
- **민감 정보를 노출하지 않는다.** 에러 메시지·응답에 리소스 존재 여부, 내부 식별자, 스택트레이스를 흘리지 않는다.
- 새 엔드포인트나 새 데이터 접근 경로를 추가할 때마다 위 항목을 자가 점검한다.
